# Events

The FileStorage behavior dispatches events while a file row is saved or
deleted. The subject of every event is the file storage table. Register
listeners on the global event manager:

```php
use Cake\Event\EventInterface;
use Cake\Event\EventManager;

EventManager::instance()->on(
    'FileStorage.afterStoringFile',
    function (EventInterface $event): void {
        $entity = $event->getData('entity');
        $file = $event->getData('file');
        // ...
    },
);
```

## Saving

In the order they fire for an upload:

| Event | Data | When |
|-------|------|------|
| `FileStorage.beforeSave` | `entity`, `storageAdapter` | Before the row is written. |
| `FileStorage.beforeStoringFile` | `entity`, `file` | Before the file is written to the adapter. |
| `FileStorage.afterStoringFile` | `entity`, `file` | After the file was written. |
| `FileStorage.blobReused` | `entity`, `file` | Instead of the two storing events, when a [deduplicated](/guide/deduplication) upload found its content already stored. Nothing is written then. |
| `FileStorage.beforeFileProcessing` | `entity`, `file` | Before variants are generated. |
| `FileStorage.afterFileProcessing` | `entity`, `file` | After variants were generated. |
| `FileStorage.afterSave` | `entity`, `storageAdapter` | After the row holds its final path and variants. |

`entity` is the `file_storage` row, `file` the library's file object,
`storageAdapter` the Flysystem adapter the row is stored on.

The two processing events also fire when variants are regenerated by the
[variant command](/images/command) or its queue task.

::: warning Listeners on the storing events and deduplication
A listener on `FileStorage.afterStoringFile`, a virus scan for example, does
not run for an upload that reuses stored content. Listen on
`FileStorage.blobReused` as well if it has to see every upload.
:::

## Deleting

| Event | Data | When |
|-------|------|------|
| `FileStorage.afterDelete` | `entity` | After the row was deleted, before its files are removed. |
